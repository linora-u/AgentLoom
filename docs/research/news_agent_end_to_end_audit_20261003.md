# news_agent 全流程耗时与交付审计（2026-10-03）

主要耗时在精筛的模型响应，以及失败后的纠错、递归拆分和重新核查。月度控制器按日串行、单日硬超时、方法变更导致缓存失效，把这些成本变成了反复处理首日而没有月度交付。Pi 确实返回了大量结果；问题是部分输出无法通过完整业务校验，恢复机制又重复执行了整组工作。

## 哪些环节耗时最多

| 环节 | Worker 调用数 | 实际 HTTP 请求数 | 单次 Worker 中位耗时 | 单次 Worker 95 分位 | 已结束 Worker 累计时间 |
|---|---:|---:|---:|---:|---:|
| 初筛 | 201 | 225 | 3.93 分钟 | 21.45 分钟 | 22.65 Worker 小时 |
| 弃选完整复读 | 90 | 90 | 4.28 分钟 | 7.45 分钟 | 6.91 Worker 小时 |
| 原始精筛，含纠错调用 | 358 | 1,526 | 9.51 分钟 | 47.57 分钟 | 100.38 Worker 小时 |
| 精筛拆分子调用，含纠错 | 960 | 3,052 | 6.87 分钟 | 18.43 分钟 | 108.63 Worker 小时 |

这些累计时间叠加了并发 Worker，**不能相加后当作用户等待时间**。精筛与拆分约占已结束调用累计时间的 **87.6%**。全部流程共 1,614 次 Worker 调用、4,900 次实际 HTTP 请求，另有少量探测和格式验证调用。

对有结束耗时的调用，逐一匹配请求和响应，再将每个调用的匹配区间之和限制在该调用耗时内：约 **97.4%** 的累计时间位于请求到响应之间。该区间包含服务端推理、原生搜索/打开页面、生成输出和网络等待，现有记录不能再精确拆成各自占比。平台工具调用累计约占 **0.35%**。

已知 HTTP 请求区间与 20 小时窗口取交集再做并集，至少 **15.95 小时**存在请求在途。剩余时间不能全部归为本地计算：还包含轮次切换、修正、停机，以及没有响应终点的请求。729 个实际请求没有报告 token 用量，其中 36 个没有记录到响应；追踪中的 `running` 标记也可能是被中断的旧状态，不能当成当前活跃进程。

已报告输入 token（含缓存）至少 **236,848,268**，输出 token 至少 **30,937,787**。这是已报告用量下界，不能当作计费金额，缓存输入与普通输入也不能按同一单价相乘。

本地离线基准：8,489 条首日完整记录按当前精筛上限重新分块耗时 **0.668 秒**；完整方法签名单次中位 **0.720 秒**。同时执行 20 次签名计算耗时 **109.28 秒**，说明反复并发扫描/哈希有明显争用，应在一轮任务开始时计算一次后共享；该探测与正在运行的任务共用机器，不能当作独占基准。它仍远小于模型调用累计耗时，不是本次 20 小时的主因。

## 主要发现与优先级

### P0：失败恢复重复执行整组分析，缺少原始任务的总预算

位置：[`baseline.py` 的 `_refined_worker_rows`](../../applications/news_agent/baseline.py#L590)、[`_recoverable_refined_error`](../../applications/news_agent/baseline.py#L697)、[`_analyze_selected`](../../applications/news_agent/baseline.py#L861)。

当前路径是：模型/SDK 内部纠错 → Python 业务校验失败后带完整输入和上次 JSON 再调用一个新 Worker → 可恢复失败再按 token 拆分 → 子组继续纠错与拆分。子组确实只携带该组的完整新闻，未发现误传整块正文；但已处理过的新闻仍会在各层重复提交、搜索和分析。每次 `_call_worker` 都创建新 Runtime 上下文。

实测窗口出现 960 次拆分子调用、最深 8 层、214 个 `stopReason=length` 响应、254 次传输重试，以及初筛/精筛合计 116 次外层纠错调用。拆分请求远多于传输重试，不能只靠调整网络重试解决。

离线复现直接运行当前 `_analyze_selected`，替换的仅是模型边界：8 条完整新闻，组级业务校验失败、单条成功，需要 **22 次 Worker 调用、56 次新闻正文提交**，最终才得到 8 条完整判断。未调用模型，也未读取收益。

**改进：**以原始任务为单位统一管理总时间、模型轮次、请求数和 token 预算；区分系统性协议错误、暂时传输故障、输出长度和单事实证据缺失。只恢复受影响的事实或字段，保留已完成的可靠证据与判断。预算耗尽写为待恢复/失败并保留所有新闻，禁止把失败当成空结果。不能只增加每次 HTTP 的超时和输出上限。

### P0：首日串行阻塞和 4 小时硬超时破坏交付进度

位置：[`replay.py::_run_day`](../../applications/news_agent/evaluation/replay.py#L196)、[`_run_month`](../../applications/news_agent/evaluation/replay.py#L219)、[`ParallelAgentExecutor`](../../src/execution/concurrency/parallel_executor.py#L19)。

月度循环先串行完成每一天的预测，任意一天退出非零就终止控制器。单日 subprocess 的 14,400 秒硬超时与模型请求的 900 秒超时彼此独立。旧 32k 输出上限轮次从北京时间 15:02 跑到 19:04，完成 89/100 个精筛块后被单日超时终止；已经花了 2,357 个 HTTP 请求，仍无完整日预测。

递归左右子组在同一个线程内顺序执行。第二个离线复现中，8 条新闻一路失败到最左侧单条，4 次调用后整块退出，右侧新闻没有进入恢复调用；失败状态阻止了不完整结果被当作成功，这一点正确，但调度无法独立推进右侧任务。新闻仍在输入中，不能说已经被删除。

**改进：**把日期、块和失败子任务变成持久化任务队列，所有日期共享**总并发 20**；一个失败子任务不占住整条恢复链，也不阻止其他日期。控制器时限到达时保存进度、结束当前执行片段，随后从同方法断点恢复。完成全月预测和正式名单冻结后才读收益，这个时序继续保留。跨日期队列改善故障隔离，不保证降低总模型成本。

### P0：方法尚未稳定就反复启动整月，缓存被正确但昂贵地失效

位置：[`_model_signature`](../../applications/news_agent/baseline.py#L157)、[`_result_is_current`](../../applications/news_agent/baseline.py#L391)、[轮次记录](../../applications/news_agent/data/evaluation/v23_formal/development_rounds.jsonl)。

完整方法签名包括所有模型配置、新闻方法文件、工作流、评估代码、根项目 `src` 和已安装桥接产物。精筛或来源规则的修正因此也会使初筛缓存失效。窗口内同一查询文本最多执行 7 次，26 个文本查询有重复，额外调用实例 127 次；不同方法重算可能是必要的，不能据此安全复用旧结论。

最新 20:42 轮次明确记录：方法从 `d870…` 变为 `f45b…`，首日 25 个旧初筛缓存全部失效。相反，19:58 的同方法重启复用了 24 个初筛成功块，只重跑失败块，说明**同方法成功缓存续跑有效**。

**改进：**先冻结完整协议，通过真实提供商的契约、时序与证据探测，再跑一个完整新闻日，随后放行全月；这只是工程门禁，不缩减最终验收新闻。完整指纹继续严格校验，不引入跨版本兼容或旧结论迁移。共同证据只在同一完整方法与截止时点下复用，原始材料与失败记录保留为审计证据。

### P1：系统性错误没有及时停止派发

位置：[`_recoverable_refined_error`](../../applications/news_agent/baseline.py#L697)、精筛执行器的 `circuit_breaker_threshold=None`、Pi 输出校验边界。

历史轮次因提供商不支持 JSON schema 的 `uniqueItems` 产生 **349 个同类拒绝**。这是已修复的协议故障，不是当前 Pi SDK 一直无响应。关闭批次熔断且把较广的校验异常视为可恢复，会让系统性错误以更多请求/子任务的形式继续出现。

**改进：**在全量派发前对真实请求体做协议检查；同一不可恢复协议错误首次确认后停止新增派发，保留未执行任务为 pending。不要将任务标为空或以删除样本完成月度。

### P1：`terminated` 流错误未进入重试，当前也在触发整日退出

位置：[`model.ts` 的 retryable 判断](../../src/runtimes/pi/bridge/model.ts#L298)、[`run_day` 的初筛失败汇总](../../applications/news_agent/baseline.py#L1163)。

20:42 新一轮初筛第 2 批对应 `run_20261003T124251949272Z_04722d1388f1`，实际响应在 **67.002 秒**后结束为 `stopReason=error`、`errorMessage=terminated`，1 次请求、0 次重试、用量未报告。当前可重试文本识别含 `stream ended`，不含单独 `terminated`；此异常被包装为普通 provider failure，使整日非零退出。窗口中共记录 317 个 `terminated` 响应，但不能断言每次都是相同上游原因。

`terminated` 本身不能定位是提供商、网络、代理还是 SDK 流处理终止，未把它归咎于 Pi SDK。**改进：**根据底层异常类型和是否收到完整终态区分流中断与明确拒绝，对没有成功终态的暂时流故障做有上限的同任务恢复；重试仍计入总任务预算。真正的协议/认证错误保持不可重试。

### P1：恢复只保留成功块，中途已完成的联网与推理无法续接

位置：[`config/system.yaml`](../../applications/news_agent/config/system.yaml#L1)、[`_call_worker`](../../applications/news_agent/baseline.py#L297)。

news_agent 关闭 checkpoint；每次调用创建新上下文，纠错与拆分会重复加载 Skill/reference 并搜索。完整成功块可以缓存，中途失败调用不能复用其完整会话进度。

**改进：**设计同一方法、输入、历史截止和任务身份下的持久会话或任务级断点，恢复已经执行的工具和可验证证据。先验证 Pi 的工具消息、终态校验和上下文预算均可恢复，再启用。checkpoint 开关本身不能自动完成这些语义。

### P1：事实核查与多 ETF 判断绑定在一次大输出中

一个 Worker 同时承担读完整新闻、首披与版本核查、多个新增/相反事实、ETF 暴露、方向与完整弃权理由。重复转载和多 ETF 映射可能重复核查同一个事实；现在跨块事件去重发生在昂贵精筛之后。

**改进：**先为同一方法内的事实建立可复用证据包，再基于证据包分析每个 ETF 映射与净方向。转载合并保留全部原文成员、完整正文与新增/相反进展；不能仅凭标题相似度合并。事实核查与映射输出分开，减少一次输出长度失败使整组工作报废的概率。提速幅度必须由同输入小规模真实对照测量，不能预先承诺。

### P2：观测汇总太晚，运行状态不等于交付状态

位置：[`replay.py::_run_month` 的 performance 汇总](../../applications/news_agent/evaluation/replay.py#L249)。

请求级追踪保留得较完整，这是此次能够量化的基础；但月度 `performance.json` 要等全月完成后才生成。控制器失败时缺少持续更新的“已完成日期、待恢复任务、重复成本、终止原因”总览，旧 `running` 状态也可能没有终态。

**改进：**独立更新执行状态与费用下界；显示成功、业务拒绝、待恢复、中断、未派发，以及完整日/月产物数。前端进度用交付分母，明确“精筛块成功”尚不是“完整新闻日预测”。

### P2：预测指纹包含未必被最终结果引用的中间 JSON

位置：[`evaluation/baseline.py::analysis_fingerprint`](../../applications/news_agent/evaluation/baseline.py#L28)。

该函数纳入整日 `refined_chunks/*.json`，包含拆分与辅助校验文件；对孤立中间文件的变化也会改变预测指纹。代码范围已确认，但本次未复现因此发生的额外完整日重跑，故列为次要风险，不作为 20 小时的主因。

**改进：**通过明确的当前任务产物清单记录所有实际参与结果的输入和证据，排除未引用的孤立中间产物，同时保留完整方法指纹。

## 建议执行顺序与可验收结果

1. **停止开发期间反复直接放行全月的流程。** 冻结协议并完成真实提供商契约验证；对现有错例验证输出预算、来源打开和精确覆盖，再完成一个完整新闻日。审计没有代替其他线程停止现有服务。
2. **先改恢复，再改并行。** 原始任务总预算、错误分类、持久 pending 状态、同方法断点和独立子任务；然后改为跨日期共享总并发 20。删掉被替代的旧恢复逻辑，不加兼容分支。
