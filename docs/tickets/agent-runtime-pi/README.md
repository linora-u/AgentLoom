## 2. 先开哪些 session

### 现在：01 和 02 可以同时做

- 新 session A：01，隔离验证发布版 Pi SDK，不能改 02 的公共源码。
- 新 session B 或当前协调 session：02，公共运行契约扩展且保持旧 smol 应用绿色。
- 两项都完成并合入同一 integration 后，由协调 session 做 03。SDK必要合同未通过，不能跳过 01 直接冻结。

第一次开工前，协调者先把已确认的 spec、计划和本地票据精确纳入准备提交，再创建 integration 分支并记录基线 SHA。当前这些文档尚未提交；只从 main 新建 worktree 不会带走它们。不要使用 git add . 把已有研究 checkout、临时目录和无关研究文档一起提交；若本地票据目录被忽略，应明确处理交付方式后再启动，不能让新 session 缺上下文。

### 03 完成后：04、05、07、08 技术上都能并行

- 04：smol 的旧实现迁移。
- 05：原生读取的生产治理闭环。
- 07：无工具 Pi Application 的原生模型与会话闭环。
- 08：平台工具/MCP 去除 smol 构造依赖。

只有三个实现者时，先开 04、05、07；04 结束后让该实现者做 08。这是资源排期，不是人为给 08 添加依赖。

### 后续解锁

- 05 完成即解锁 06；06 可以与 07/08/09 并行。
- 05、07、08 完成并集成，才解锁 09。
- 09 完成后可启动 11；06 也完成后可启动 10；04 也完成后可启动 13。
- 10 完成后启动 12，可以和未结束的 11/13 并行。
- 11、12、13 完成并集成后启动 14；其传递依赖已经覆盖其他全部任务。14 串行做最终收口、验收和合并 main。

## 4. 推荐人员分工与 worktree

| session 角色 | 建议连续承接 | 独占内容 |
| --- | --- | --- |
| 协调/集成 | 准备提交、02、03、各票接线/合入、14 | 公共契约、registry/readiness、共享配置与最终集成 |
| SDK验证 | 01 | 隔离PoC、实际发布包证据；完成后可以转其他任务 |
| smol/平台工具 | 04 → 08 → 11 | smol adapter迁移；随后平台工具；最后混合与记忆验收 |
| 工具治理 | 05 → 06 | Gateway、授权、journal、文件/Shell保护、产物和证据 |
| Pi | 07 → 09 → 10 → 12 | Pi adapter/bridge、原生调用、工具包装、session恢复 |
| 发行，可由协调者兼任 | 13 | Python依赖/锁文件、安装、CLI错误路径、CI |

任务与 session 不是一对一：可让一个 session 连续做同一条链；上下文过长时再换新 session，但仍按票据号和已集成的基线交接。一个 worktree 同时只允许一个 session 修改。

每票使用 codex/pi-tNN-主题 分支；worktree 放在仓库外的 AgentLoom-worktrees/tNN。先从 integration 取得包含所有依赖的已验证 commit，再创建分支。相邻串行任务可以复用原 session/worktree，但必须确认依赖提交已包含且没有未提交混杂成果。

不同 worktree 使用独立虚拟环境、Node安装、runtime目录、memory测试数据库和checkpoint；避免 editable install 指向另一个 worktree。凭证使用私有未跟踪配置，提交和证据报告不包含秘密。

## 5. 文件冲突与阶段能力

这里细化原 worktree 计划的 C0/S1/G1/P1/V1/I0，而非另建一套架构：

| 原阶段 | 新票据 |
| --- | --- |
| C0契约与兼容 | 01、02、03 |
| S1 smol收口 | 04 |
| G1治理/公共服务 | 05、06、08 |
| P1 Pi实现 | 07、09、10、12 |
| V1端到端验收 | 每票自己的行为验收＋11，最终14重跑 |
| I0发行/集成 | 每票及时接线＋13＋14 |

执行时采用以下更细所有权：

- 01 只写隔离验证材料，不与 02 共改产品源码。
- 02/03 固定公共模型/运行定义、metadata、IPC与结算合同；变更由协调者生成统一合同提交，各分支更新后再继续。
- 04 只迁移 smol 实现及移交清单，不提前删除 08 尚未迁走的入口。
- 05→06 顺序拥有生产 Gateway、Hook/权限、journal和artifact实现；08只拥有平台工具定义、loader/MCP及必要memory接入。
- 07→09→10→12 顺序拥有 Pi adapter/bridge。09 与 06 并行时只消费 05 已固定的接口，不编辑治理实现。
- 11 主要维护混合/记忆应用与独立oracle，公共协作接线交协调者处理，不编辑 Pi bridge、恢复或治理源码。
- 13 独占 Python packaging/lock、安装和CI；bridge manifest/Node lock由Pi链持有，13只消费并协调必要依赖变更。
- 14 不能变成“补所有未做功能”的大票；恢复由12、Goal由09、真实产物由10完成后才进入14。

07 必须在本票完成前经过真实 registry/readiness 接线，因此可以独立演示。它只发布能力受限的无工具运行；09通过才开启只读/平台工具/Goal，10通过再开启写入/Shell，12通过才声明恢复。不要把一个空壳 Pi 注册后就宣称完整支持，也不能把注册全部拖到14导致前票只有mock测试。

共享源码补丁由协调者串行合入并提供验收SHA，但属于对应票的完成责任；开发者不能以“只做adapter，等最后接线”为由提前关闭票。

## 6. 给新 session 的启动说明

复制对应票据内容，并附下面这段要求即可。不要仅发送“去做Pi接入”：

> 实现指定的 NN 号票据。先读取核心规格、执行索引和该票完整验收条件，核对所有 Blocked by 任务的实际提交已包含在 integration 基线。使用独立 codex/ 分支和 worktree，只修改本票拥有的模块；公共合同或共享入口变更先交协调者串行处理。完成后给出提交SHA、测试命令和结果、产物证据及未完成项，不自行合并 main，不顺手开发下一票或删除其他工作成果。

每次交接提供四项：票号、基线SHA、本票分支/提交SHA、验收证据。协议版本和 Node/Pi 版本有变化时一起说明。

## 8. 发布与合并

本轮先形成可审阅的一票一文件草稿。确认粒度、依赖和是否需要合并/再拆后，按项目配置发布到 GitHub Issues，按依赖顺序创建并使用实际issue标识写入阻塞关系；平台支持时使用原生blocking关系。发布不修改或关闭历史parent issue。

日常提交先合入 integration，依赖票合入且通过相关验证才解锁下一票。所有功能和安装机制就绪后由14清除过渡接口、验证最终树、处理main前进并合并。其他session不各自向main合入，更不能强推或丢弃别人的修改。

当前没有任何票已完成，没有GitHub issue号，也没有实际开发worktree。打开新session前先检查票据和基线，避免把“拆分完成”误当成“前置任务已完成”。
