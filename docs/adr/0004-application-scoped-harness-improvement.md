# 以完整应用版本进行 Harness 改进与采用

2026-10-20，确认设计方向，尚未实现。应用包含相互依赖的多个 Agent 和子 Agent，逐 Worker 独立采用会遗漏协作影响，并可能组合出接口不一致的配置。

由 Application YAML 启用改进机制，以完整 Application Harness 作为候选、试跑、比较与采用单位，覆盖提示词、Skill、工具配置，并允许增删 Agent 和调整委派关系。完整应用是固定优化单位，不额外设置只有一个取值的优化粒度参数。相对于局部 Worker 优化，这要求完整配置版本、整图校验与整应用试跑；应用目标和业务验收约束保持固定，新闻应用继续满足完整覆盖、独立校验与证据截止要求。

反馈方式和递归预算由配置选择，同时支持无标签对照改进与开发集评分反馈，以及并行探索与连续改进。改进器角色也可通过 Agent YAML 定义；具体配置值在单次运行开始时冻结，不要求用户在设计阶段选定唯一长期方案。

用户进一步确认：候选通过可校验的配置、提示词与 Skill 调整真实编排，将应用 Python 中需要变化的调度接到配置。框架及应用适配层为支持这些配置所需的代码改造属于实施工作，不等于向候选开放任意源码编辑。业务 Python 与工具源码的直接修改作为单独声明的能力，本轮不隐式开放；这样既能验证编排改动确实影响执行，也保留清晰的候选修改边界。

用户确认显式启用应用后按任务触发改进。该路径实际执行基线、候选和组合版本中的业务 Agent/subagent，并选择已经执行的结果交付；不是仅生成改进配置。首版直接由 enabled 决定该行为，不再增加额外触发模式字段。

按用户要求进一步收敛必要性：首版沿用 Harness² 的 final 选择与改进经验库，不加入自动替换后续默认版本、基线回退选择模式或预算耗尽交付策略。探索规模以 mode/k 配置，不额外建设实验总金额/token配额与预留结算系统。完整资源冻结、业务状态隔离、原业务验收和防重复恢复仍是整应用试验必需条件；这保留跨任务经验积累，同时避免引入当前闭环不需要的控制体系。
